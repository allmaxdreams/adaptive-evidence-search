# **Adaptive Ontology-Driven Evidence Search**

## **Адаптивний онтологічно-керований пошук доказів**

## **1\. Призначення**

Framework призначений для пошуку й аналізу інформації у складних доменах:

* технологіях;  
* політиці;  
* бізнесі;  
* безпеці;  
* культурі;  
* суспільних процесах;  
* конкурентній розвідці;  
* стратегічному прогнозуванні.

Його мета полягає не в тому, щоб знайти найбільше джерел, а в тому, щоб:

1. правильно визначити об’єкт пошуку;  
2. знайти прямі й непрямі сліди явища;  
3. відокремити заяви від доказів;  
4. виявити альтернативні пояснення;  
5. сформувати знання, достатнє для конкретного рішення.

Основна логіка:

Питання  
→ вибір глибини пошуку  
→ модель явища  
→ карта інформаційних слідів  
→ портфель запитів  
→ discovery  
→ verification  
→ синтез  
→ рішення  
→ оновлення моделі

---

# **2\. Search Mode Gate**

Перед початком система повинна визначити, який рівень дослідження справді потрібен.

## **Mode 1\. Direct Lookup**

Використовувати, якщо:

* питання має одну конкретну фактичну відповідь;  
* існує очевидне авторитетне джерело;  
* немає суттєвої суперечності;  
* користувачу не потрібне причинне пояснення.

Приклади:

* правила ручної поклажі;  
* дата події;  
* офіційна технічна характеристика;  
* чинний тариф;  
* формальна вимога закону.

Процес:

Питання  
→ первинне джерело  
→ перевірка актуальності  
→ відповідь

Не потрібно будувати онтологію, граф доказів чи конкуруючі гіпотези.

---

## **Mode 2\. Structured Search**

Використовувати, якщо:

* інформація розподілена між кількома джерелами;  
* термінологія неоднозначна;  
* потрібно визначити тренд, структуру ринку або стан системи;  
* прямий пошук дає фрагментарну картину;  
* потрібне порівняння кількох акторів або підходів.

Приклади:

* нові напрями в певній технології;  
* зміни на ринку;  
* розвиток політичної реформи;  
* позиціонування конкурентів;  
* культурний або споживчий тренд.

Процес:

Дослідницьке питання  
→ легка онтологія  
→ 2–3 робочі гіпотези  
→ карта джерел  
→ портфель запитів  
→ синтез

---

## **Mode 3\. Recursive Evidence Search**

Використовувати, якщо:

* явище частково приховане;  
* актори мають стимули маніпулювати інформацією;  
* потрібен пошук слабких сигналів;  
* висока ціна помилки;  
* джерела суперечать одне одному;  
* потрібно створити постійний моніторинг;  
* дослідження стане основою стратегічного рішення.

Приклади:

* приховані технологічні розробки;  
* політичні коаліції;  
* оборонні програми;  
* реальна зрілість продукту;  
* непрямі ознаки зміни стратегії компанії;  
* системні вразливості.

Процес:

Дослідницький контракт  
→ предметна онтологія  
→ інформаційна онтологія  
→ конкуруючі гіпотези  
→ карта слідів і антислідів  
→ discovery  
→ verification  
→ граф доказів  
→ спростувальний пошук  
→ синтез  
→ оцінювання  
→ оновлення онтології

---

# **3\. Визначення дослідницького контракту**

Для Mode 2 і Mode 3 система визначає:

## **Питання**

Що саме потрібно зрозуміти?

## **Контекст рішення**

Для якого рішення потрібна інформація?

## **Об’єкт**

Яка система, технологія, організація, процес або конфлікт досліджується?

## **Межі**

* часовий період;  
* географія;  
* мови;  
* типи акторів;  
* допустимі джерела;  
* юридичні й етичні обмеження.

## **Необхідна точність**

Потрібно:

* знайти сигнал;  
* сформувати гіпотезу;  
* підтвердити факт;  
* оцінити тренд;  
* підготувати стратегічне рішення?

## **Формат результату**

* коротка відповідь;  
* evidence brief;  
* карта акторів;  
* карта технологій;  
* сценарії;  
* watchlist;  
* база знань;  
* регулярний моніторинг.

# **5\. Друга онтологія: інформаційна видимість**

Для Mode 3 потрібно окремо моделювати не лише явище, а й те, як воно стає видимим.

Основні питання:

* хто має інформацію;  
* хто зацікавлений її оприлюднити;  
* хто зацікавлений її приховати;  
* які документи неминуче виникають;  
* які залежності залишають відкриті сліди;  
* де інформація може бути викривлена;  
* де її відсутність справді є значущою.

Структура:

Activity  
→ requires → Resource  
→ produces → Artifact  
→ becomes\_visible\_in → Source  
→ supports → Claim

Наприклад:

Закрита розробка  
→ потребує → FPGA-інженерів  
→ створює → вакансії  
→ згадує → real-time signal processing  
→ формує → непрямий сигнал про напрям R\&D

# **6\. Гіпотези**

Для Mode 2 достатньо 2–3 робочих гіпотез.

Для Mode 3 потрібно сформувати:

## **H1: основна гіпотеза**

Найімовірніше пояснення.

## **H2: альтернативна гіпотеза**

Інше правдоподібне пояснення тих самих сигналів.

## **H0: нульова гіпотеза**

Сигнали випадкові або не пов’язані між собою.

## **HV: гіпотеза невидимості**

Явище існує, але не залишає очікуваних відкритих слідів.

Для кожної гіпотези визначити:

hypothesis:  
  statement:  
  expected\_evidence:  
  contradicting\_evidence:  
  hidden\_variables:  
  confidence:

Не потрібно створювати більше гіпотез, ніж система здатна реально перевірити.

# **9\. Discovery і Verification**

Ці процеси мають бути розділені.

## **Discovery**

Мета:

* знайти нові поняття;  
* виявити нових акторів;  
* знайти слабкі сигнали;  
* розширити карту джерел;  
* визначити суміжну лексику.

Допустимі:

* форуми;  
* Reddit;  
* соціальні мережі;  
* блоги;  
* коментарі;  
* неперевірені згадки.

## **Verification**

Мета:

* перевірити конкретне твердження;  
* знайти первинне джерело;  
* встановити дату події;  
* перевірити незалежність джерел;  
* знайти контрдокази;  
* відокремити факт від інтерпретації.

Принцип:

> Слабке джерело може створити сильну пошукову гіпотезу, але не повинно автоматично створювати сильний висновок.

# **10\. Claims, а не документи**

Основною одиницею аналізу має бути твердження.

Кожне твердження містить:

claim:  
  statement:  
  entity:  
  event\_date:  
  publication\_date:  
  source:  
  source\_type:  
  primary\_or\_secondary:  
  evidence\_status:  
  independence\_group:  
  supports\_hypothesis:  
  contradicts\_hypothesis:  
  alternative\_interpretation:  
  confidence:

Один документ може містити одночасно:

* факт;  
* рекламу;  
* прогноз;  
* припущення;  
* цитування іншого джерела.

Тому документ не повинен отримувати єдину загальну оцінку.

# **11\. Незалежність доказів**

Кількість публікацій не дорівнює кількості доказів.

Система повинна визначати provenance:

Press release  
→ News article A  
→ News article B  
→ Blog  
→ Social post

Це одна доказова лінія.

Незалежними можна вважати джерела, якщо вони:

* мають різні первинні підстави;  
* не повторюють один документ;  
* отримали інформацію незалежно;  
* використовують різні datasets;  
* представляють різні типи слідів.

Сильна триангуляція:

Contract  
\+ patent  
\+ vacancy  
\+ prototype demonstration

---

# **12\. Оцінювання знахідок**

Не використовувати один інтегральний score як основний.

Оцінювати окремо:

* **relevance** — відповідність питанню;  
* **reliability** — надійність;  
* **independence** — незалежність від інших джерел;  
* **specificity** — наявність перевірюваних деталей;  
* **recency** — актуальність;  
* **novelty** — нова інформаційна цінність;  
* **actionability** — вплив на рішення;  
* **visibility bias** — ризик викривлення публічної картини.

Приклад:

Reddit-коментар

relevance: high  
reliability: low  
novelty: high  
independence: unknown  
actionability: medium

Результат:

> Сильна зачіпка, слабкий доказ.

# **13\. Синтез**

Фінальний результат має бути структурований за рівнями знання.

## **Confirmed facts**

Безпосередньо підтверджені факти.

## **Strong inferences**

Висновки, підтримані кількома незалежними доказовими лініями.

## **Working hypotheses**

Правдоподібні, але недостатньо підтверджені пояснення.

## **Contradictions**

Твердження, які не складаються в одну картину.

## **Knowledge gaps**

Інформація, відсутність якої найбільше обмежує висновок.

## **Alternative explanations**

Інші моделі, що пояснюють ті самі сигнали.

## **Update triggers**

Події або дані, після яких висновок потрібно переглянути.

Формат ключового висновку:

conclusion:  
  claim:  
  supporting\_evidence:  
  contradicting\_evidence:  
  alternative\_explanation:  
  confidence:  
  decision\_implication:  
  update\_trigger:

# **14\. Правила зупинки**

Пошук завершується, коли:

* нові джерела переважно повторюють відоме;  
* основні твердження мають достатню доказову підтримку;  
* альтернативні гіпотези перевірені;  
* критичні прогалини визначені;  
* подальший пошук має низьку очікувану цінність;  
* отриманого рівня впевненості достатньо для рішення.

Пошук продовжується, якщо:

* ключовий висновок тримається на одному джерелі;  
* дані суперечливі;  
* з’явився новий актор або новий тип артефакту;  
* ціна помилки висока;  
* онтологія суттєво змінилася;  
* знайдений контрдоказ руйнує попередній синтез.

# **15\. Рекурсивне оновлення**

Після кожного циклу система повинна перевірити не лише предмет дослідження, а й власний метод.

## **Ontology review**

* Які сутності були відсутні?  
* Які категорії виявилися надто широкими?  
* Які зв’язки були неправильними?  
* Яка термінологія з’явилася під час пошуку?

## **Query review**

* Які запити дали найбільше нового знання?  
* Які дали переважно шум?  
* Які джерела були недооцінені?  
* Які мови або регіони не охоплено?

## **Evidence review**

* Де виникла хибна впевненість?  
* Які джерела виявилися залежними?  
* Які висновки не пройшли перевірку?  
* Які контрдокази були знайдені запізно?

## **Efficiency review**

* Скільки джерел було потрібно для одного корисного висновку?  
* Які етапи дублювали роботу?  
* Чи був обраний правильний Search Mode?  
* Чи можна було завершити пошук раніше?

# **16\. Agentic architecture**

## **1\. Mode Selector**

Вибирає Direct Lookup, Structured Search або Recursive Evidence Search.

## **2\. Research Planner**

Формує дослідницький контракт і критерії завершення.

## **3\. Ontology Agent**

Створює мінімально достатню онтологію.

## **4\. Visibility Agent**

Моделює інформаційні сліди, джерела й стимули до приховування.

## **5\. Hypothesis Agent**

Формує основну, альтернативну, нульову та visibility-гіпотези.

## **6\. Query Agent**

Створює портфель пошукових запитів.

## **7\. Source Collectors**

Працюють із конкретними каналами:

* web;  
* news;  
* academic;  
* patents;  
* government;  
* procurement;  
* GitHub;  
* Reddit;  
* corporate;  
* social.

## **8\. Claim Extractor**

Витягує твердження, сутності, події, дати й зв’язки.

## **9\. Evidence Critic**

Перевіряє надійність, provenance, незалежність і контрдокази.

## **10\. Synthesizer**

Формує карту знань, висновки, сценарії та implications.

## **11\. Evaluator**

Оцінює coverage, novelty, calibration, actionability та efficiency.

## **12\. Update Agent**

Оновлює онтологію, словник, джерела й стратегії пошуку.

Агенти потрібні там, де необхідні:

# **19\. Критерії якості framework**

Framework оцінюється не кількістю джерел, а такими показниками:

## **Coverage**

Чи охоплено основні сутності, процеси й типи джерел?

## **Novelty**

Чи знайдено те, чого не дав би звичайний keyword search?

## **Evidence quality**

Чи спираються висновки на первинні й незалежні джерела?

## **Counterevidence**

Чи проводився реальний пошук спростувань?

## **Calibration**

Чи відповідає впевненість якості доказів?

## **Reproducibility**

Чи можна відтворити шлях до висновку?

## **Efficiency**

Чи виправдовує якість результату вартість пошуку?

## **Actionability**

Чи змінює результат рішення, пріоритет або наступний крок?

# **20\. Остаточна формула**

Search Mode  
визначає необхідну глибину.

Онтологія  
визначає, що може існувати.

Модель видимості  
визначає, де це залишає сліди.

Гіпотези  
визначають, що перевіряти.

Портфель запитів  
захищає від вузької термінології.

Discovery  
розширює карту.

Verification  
перетворює сигнали на докази.

Синтез  
перетворює докази на рішення.

Рекурсія  
покращує наступний цикл.

Головний принцип:

> Використовуй найпростішу версію пошуку, здатну дати надійну відповідь. Поглиблюй метод лише тоді, коли складність реальності цього вимагає.
